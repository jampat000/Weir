# Weir v1.0.0-rc.3

Date: 2026-10-07

> **Early days.** Weir is early, and it is in active, hard testing. Expect rough edges. If something is wrong or confusing, please report it on [GitHub issues](https://github.com/jampat000/Weir/issues).

This release candidate makes Weir safe beside a download client that is still seeding, sets Weir up from Deluno with nothing to type, and fixes what the first full Deluno and Weir test found.

## Important: originals in a linked workflow are never touched

- **A workflow linked to a media manager never deletes or moves the original download.** That covers Deluno, Sonarr, Radarr and "Something else". The file in your download client's folder, its side files (such as `.nfo`) and its release or season folder all stay where they are, whatever "remove the original after cleaning" says. Your download client and media manager decide when it goes, for example once seeding ends. Only a "Weir only" workflow can still remove its originals.
- **A workflow linked to Deluno is cleaned only when Deluno hands Weir the file.** Weir's own scan of the watched folder no longer picks those files up, so a download is never cleaned twice, and it is never cleaned before Deluno says it's finished.
- **Why:** in 1.0.0-rc.2, saving a Deluno-linked workflow made Weir scan the download folder. It cleaned a film Deluge was still seeding, then removed the torrent's small side files from Deluge's folder. If you run rc.1 or rc.2 with a linked workflow, update now. In your download client, re-check any torrent that lost files, and it fetches them again.

## What Changed

- **Weir sets itself up from Deluno.** When Deluno connects to Weir (Deluno's **Connect Weir**), Weir fills in a workflow for each Deluno library that sends its downloads to Weir, and links it to Deluno:
  - its watched folder is where that library's downloads arrive;
  - its output folder is the processed folder Deluno imports from.

  Weir keeps them in step when they change in Deluno. They show as **From Deluno** in Weir's editor; change them in Deluno. Weir's own work folder stays yours to set (until you do, Weir uses its own temporary folder), as do the rules profile and the schedule. **Unlink** stops the syncing for that workflow. Sonarr, Radarr and "Something else" workflows are set up by hand as before.
- **A refused hand-off says why, and is logged.** When a media manager hands Weir a file that no workflow's watched folder contains, the answer names the workflows Weir checked and the folder each one watches, and says what to set. The refusal is also written to Weir's log, so it shows in **System › Logs**.
- **Older firewall rules are widened once, by themselves.** If you turned on **Devices on my network** under 1.0.0-rc.1, Weir's rule covered Private and Domain networks only. After this update Weir asks Windows once, with the usual administrator prompt, to extend the rule to every network type. It asks only once, and never on a silent or unattended start.
- **The side menu shows just your name.** The line under it, which repeated your role and the computer's name, is gone. The computer's name is on **System › About**.

## Fixes And Stability

- After an update was installed, **System › About** could still offer to restart for that same update. It no longer does.

## Upgrade Notes

- Windows: **Check for updates** in the tray or **System › About**, or install `Weir-win-Setup.exe` over the top. Existing data is kept.
- If you paused Weir because of the seeding problem above, update first, then resume.
- Docker: change the image to `ghcr.io/jampat000/weir:1.0.0-rc.3`, then `docker compose pull && docker compose up -d`.

## Docker

- `ghcr.io/jampat000/weir:1.0.0-rc.3`
- Images are published for `linux/amd64` and `linux/arm64`, and run the .NET build of the Weir server.
